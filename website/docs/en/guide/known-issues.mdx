# Known issues

When a run surfaces an error that looks like a vitest-agent bug, check it here
first. Several common signatures are upstream Vitest behavior, an
already-shipped fix, or a misconception.

## `DataStoreError` on a UNIQUE collision

**Status: live.** Concurrent agent registration (on `idempotency_key`) or
concurrent turn writes (on `(session_id, turn_no)`) can race the persistence
layer's check-then-insert and surface a `DataStoreError` carrying
`UNIQUE constraint failed`. It is not data corruption — retry the operation.

## `coverage/.tmp … ENOENT coverage-0.json`

**Status: fixed for MCP `run_tests` invocations, live everywhere else.** Two
Vitest processes running at once (for example a CLI run alongside the
`vitest-vscode` extension) share Vitest's default `coverage.reportsDirectory`,
and one can delete the temp dir the other is using. Each `run_tests`
invocation now gets its own throwaway reports directory, so concurrent MCP
runs no longer collide — one consequence is that html/lcov artifacts from an
MCP run land in that throwaway directory rather than `./coverage`, which
costs nothing because MCP consumers read coverage from SQLite. Two concurrent
direct `vitest run` processes still collide: give each its own
`coverage.reportsDirectory`, or serialize them. Update `@vitest-agent/mcp` if
you still see this on MCP runs.

## `persistence failed — results above were rendered but NOT recorded`

**Status: expected.** The reporter renders results and persists them as two
separate phases. When the write phase fails — a locked database, an
unwritable data directory, a migration that cannot run — the results still
render and this line goes to stderr with the underlying error appended.
Trust what you see on screen; do not trust history for that run. Nothing
reached SQLite, so classifications are absent from the render and
`test_status`, `test_history`, and coverage trends stay at their previous
values until a run persists successfully. Fix the cause named in the message
and rerun.

## `0 tests collected` on a run you expected to be green

**Status: expected.** A run that collects nothing is reported as a warning
rather than a pass, because zero tests almost always means a wrong working
directory, a filter that matched nothing, or a load-time error — not an
empty suite. The agent-facing totals line also carries
`across N files` whenever the collected module count is known, so a lower N
than you expect is the signal that files failed to load.

## `MaxPerformanceEntryBufferExceededWarning`

**Status: resolved.** Fixed in a shipped `@vitest-agent/reporter` release — the
live renderer now drains Node's user-timing buffer after each render cycle, so
React 19's development-reconciler `performance.measure()` entries no longer
accumulate. Update `@vitest-agent/reporter` if you still see it.

## `Cannot use two functions as arguments` with `@effect/vitest`

**Status: resolved.** The plugin's tag transform used to rewrite `test()` and
`it()` call arguments, which corrupted wrapper testers with a
`(name, self, timeout)` signature — `@effect/vitest`'s `it.effect` failed with
`Cannot use two functions as arguments` or collected 0 tests. The transform
now prepends a file-level tag prelude and lets Vitest's runner propagate the
tags, so every declaration form inherits classification tags without having
its arguments touched. Update `@vitest-agent/plugin` if you still see it.

## Stale test counts after moving or adding files

**Status: resolved.** The long-lived MCP server cached discovery results per
process, so adding, removing or moving test files could leave a warm MCP
reporting counts from before the change until it was restarted. Discovery now
detects when the set of test files on disk changes and re-scans automatically,
so counts stay fresh with no restart. Update `@vitest-agent/plugin` if you
still see stale counts. The `run_tests` result carries `discoveryLastScannedAt`
— an ISO timestamp of the last real disk scan — so you can confirm a count came
from a fresh scan.

## `[vite] Failed to load source map` / `ENOENT … .js.map` under coverage

**Status: resolved.** Under v8 coverage, Vite core repeatedly logged
`Failed to load source map` and `ENOENT: … .js.map` warnings for dependencies
whose npm tarball ships a `.js` file with a dangling `sourceMappingURL` but no
`.map` sibling — the TypeScript package is the usual culprit. The warnings are
harmless. The plugin now installs a Vite logger filter that drops exactly this
noise and passes every other warning through, so test output under coverage
stays clean with no configuration. Update `@vitest-agent/plugin` if you still
see it.

## A run that rebuilds `dist/` mid-run

**Status: expected.** A host project's Vitest `globalSetup` can call
`AgentPlugin.runScript(...)` (for example `pnpm turbo run build:dev`), which may
transiently rebuild `dist/` during the run. That is the host project's
configuration, not a broken workspace.
