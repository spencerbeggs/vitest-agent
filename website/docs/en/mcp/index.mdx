# @vitest-agent/mcp

The `vitest-agent-mcp` MCP server bin, built on Effect's native `McpServer` (`effect/unstable/ai`). Exposes action-keyed tools over stdio that give LLM agents structured access to test data, coverage, history, failure signatures, TDD lifecycle state, and more. Also surfaces six framing-only prompts.

This package is a regular dependency of `@vitest-agent/plugin`, and the plugin declares the `vitest-agent-mcp` bin itself as a shim over this package's `./main` entry — so installing the plugin links the bin on every package manager. Install `@vitest-agent/mcp` directly only if you run the MCP server standalone.

## Features

- **30 action-keyed tools** — per-CRUD families collapse into single tools dispatching on an `action` discriminator; covers `test_status`, `test_overview`, `test_coverage`, `test_errors`, `run_tests`, `note`, `hypothesis`, `tdd_task`, `tdd_goal`, `tdd_behavior`, `tdd_progress_push`, and more
- **Six framing prompts** — `triage`, `why-flaky`, `regression-since-pass`, `explain-failure`, `tdd-resume`, and `wrapup`
- **Idempotent writes** — `tdd_task`, `tdd_goal`, `tdd_behavior`, and `hypothesis` create-actions are idempotent on derived keys; a replay carries `_idempotentReplay: true`
- **Strict tool inputs** — an unknown key is rejected with an error naming it and listing the accepted params, so a mistyped scope param fails loudly instead of running wider than intended; numeric params are strict on the wire too, so send `"limit": 5`, not `"limit": "5"`
- **Session-surviving error handling** — a handler that dies returns a structured `UnexpectedToolError` envelope, every log line goes to stderr (stdout is the JSON-RPC wire), and a stray unhandled rejection after the transport connects is logged rather than killing the server mid-session
- **Effect Schema end to end** — tool inputs, outputs, and prompt arguments are Effect `Schema` values; the served JSON Schema is generated from them. No MCP SDK, no tRPC, no zod

## Install

```bash
npm install --save-dev @vitest-agent/mcp
# or
pnpm add -D @vitest-agent/mcp
```

## Quick start

Start the MCP server over stdio. With `@vitest-agent/plugin` installed the bin is already linked:

```bash
npx vitest-agent-mcp
# or, standalone without the plugin
npx --yes @vitest-agent/mcp
```

The server reads the SQLite database written by `AgentPlugin` via the same XDG-derived path, so a single test run populates data for all tools. It logs only to stderr — stdout is the JSON-RPC wire — and exits 0 when the client closes stdin cleanly.

For embedding, `ServerLayer({ version })` is the whole server as an Effect `Layer` over any `Stdio` implementation, and the `Kit` toolkit, `toolHandlers`, `PromptsLayer`, `registerStrictToolkit`, and `McpSession` are exported from the programmatic barrel. The process-owning `main()` lives on the `@vitest-agent/mcp/main` subpath.

## Tool surface

Tools are organized into families. Each family is a single MCP tool that dispatches on an `action` (or `kind`) discriminator:

### Query tools

| Tool | What it returns |
|------|-----------------|
| `test_status` | Pass/fail summary for the latest run |
| `test_overview` | Per-file breakdown of the latest run |
| `test_coverage` | Coverage percentages and threshold status |
| `test_errors` | Failure details with stack frames |
| `test_history` | Recent run history for a project, narrowable to one test or one file |
| `test_trends` | Direction and run count for the trend line |

### Action tools

| Tool | Actions |
|------|---------|
| `run_tests` | Spawn a Vitest run from within an agent session |
| `note` | `create`, `list`, `get`, `update`, `delete`, `search` |
| `hypothesis` | `record`, `validate` |
| `tdd_task` | `start`, `end`, `get`, `resume` |
| `tdd_goal` | `create`, `list`, `get`, `update` |
| `tdd_behavior` | `create`, `list`, `get`, `update` |
| `tdd_progress_push` | Publish an orchestrator progress event to the main agent |
| `inventory` | `project`, `module`, `suite`, `session` |
| `test` | `list`, `get`, `for_file` |
| `register_agent` | Register an agent session with the data store |

### `run_tests`

The `run_tests` tool spawns a Vitest run synchronously and returns the structured output. It supports a typed `tags` filter:

```json
{
  "tool": "run_tests",
  "input": {
    "project": "my-package",
    "tags": {
      "all": ["unit"],
      "none": ["slow"]
    }
  }
}
```

The three sub-filters (`all`, `any`, `none`) AND together. `run_tests` returns `{ kind: "no-match" }` instead of an empty result when no files match a supplied filter, so agents can distinguish a filter mismatch from a genuine zero-test project.

A successful run echoes the filter set it used on `scope`:

```json
{
  "kind": "ok",
  "scope": { "project": "my-package", "files": [], "tags": { "all": ["unit"], "none": ["slow"] } },
  "projectRoot": "/Users/me/code/my-repo"
}
```

Unknown keys are rejected rather than dropped, so a misspelled param cannot widen a run without the caller noticing.

A run with no `projectRoot` anchors at the directory of the vitest config found by walking up from the server's working directory — still the wrong tree once you are working in a git worktree, since the walk starts where the server booted. Pass `projectRoot` to run against a different checkout of the same repository; it is validated and used verbatim, and the resolved value comes back on every `ok` and `no-match` result. See the [MCP tool reference](/mcp/tools) for the anchoring and validation rules.

## Progress notifications

`tdd_progress_push` is how the TDD orchestrator reports progress to the main agent. The tool validates the payload against the `ChannelEvent` schema, enriches it server-side with the tree coordinates, and publishes it as a standard MCP `notifications/message` frame with `logger: "vitest-agent/channel"`. Clients that subscribe to logging notifications receive it; there is no custom notification method to register. The tool always returns `{ ok: true }` — delivery is best-effort.

## Framing prompts

Six prompts orient agents toward the right tool sequence without pre-fetching data:

| Prompt | Use |
|--------|-----|
| `triage` | Start of a session — what needs attention? |
| `why-flaky` | Investigate a flaky test |
| `regression-since-pass` | Find what changed since a test last passed |
| `explain-failure` | Explain a specific failure in context |
| `tdd-resume` | Resume a TDD task after an interruption |
| `wrapup` | End-of-session review nudge |

Prompts are listed by name and description only; the protocol library does not advertise a separate `title` field, so a client that shows titles falls back to the name.

## Claude Code plugin integration

When the Claude Code plugin is active, the MCP server receives the host session context automatically via env vars set by the SessionStart hook (`VITEST_AGENT_CHAT_ID`, etc.). Tool calls from the plugin's TDD subagent are pre-authorized via the plugin's allowlist — no permission prompt for standard operations.
