# Packages

The vitest-agent ecosystem is split across eight npm packages. Most users install a single package and get the rest transitively.

## Package map

| Package | Role |
|---------|------|
| [@vitest-agent/plugin](/plugin) | Vitest plugin — `AgentPlugin()`, project discovery, coverage policy, failure classification, reporter chain; the carrier that declares the `vitest-agent` and `vitest-agent-mcp` bins |
| [@vitest-agent/sdk](/sdk) | Platform-free core — Effect Schemas, reporter/dispatcher contracts, tagged errors, pure formatters and utilities, the pure `dispatch` entry, published JSON schemas |
| [@vitest-agent/engine](/engine) | Platform half — Effect services and live layers, SQLite data layer and migrations, `PlatformLive`, project-directory and XDG path resolution, hook programs, session recovery, testing utilities |
| [@vitest-agent/reporter](/reporter) | Default reporter — `DefaultVitestAgentReporter`, Ink live-mount lifecycle, contract re-exports, dispatch helpers |
| [@vitest-agent/ui](/ui) | Rendering primitives — `RunEvent` reducer, 12-cell dispatcher matrix, Ink components, PubSub channel, synthesizers |
| [@vitest-agent/cli](/cli) | CLI bin — `doctor`, `db`, `agent` namespace for database management and hook plumbing |
| [@vitest-agent/mcp](/mcp) | MCP server bin — 30 action-keyed tools and six prompts over stdio, built on Effect's native `McpServer` |
| [@vitest-agent/sidecar](/sidecar) | Native SEA binary — fast-path `inject-env` for the Claude Code plugin's PreToolUse hook |

## Dependency flow

Packages depend on each other in one direction:

```
plugin → reporter → ui → sdk
plugin → engine → sdk
cli    → engine → sdk
mcp    → engine → sdk
```

`@vitest-agent/sdk` is the platform-free core with no internal dependencies. `@vitest-agent/engine` adds the services, SQLite, and platform resolution on top of it, and is what `cli`, `mcp`, and `plugin` build on. `sidecar` has no runtime workspace dependencies — the per-platform child packages bundle `@vitest-agent/sdk/dispatch` into the SEA at build time.

The full transitive chain triggered by installing `@vitest-agent/plugin`:

```
@vitest-agent/plugin            (declares the vitest-agent and vitest-agent-mcp bins)
  ├── @vitest-agent/reporter (dependency)
  │   └── @vitest-agent/ui (dependency)
  │       └── @vitest-agent/sdk (dependency)
  ├── @vitest-agent/engine (dependency)
  │   └── @vitest-agent/sdk (dependency)
  ├── @vitest-agent/cli (dependency, exact-pinned)
  │   ├── @vitest-agent/engine (dependency)
  │   └── @vitest-agent/sidecar (dependency)
  │       └── @vitest-agent/sidecar-<platform> (optional, platform-matched)
  └── @vitest-agent/mcp (dependency, exact-pinned)
      └── @vitest-agent/engine (dependency)
```

## Which package do I install?

**Almost always: just `@vitest-agent/plugin`.**

```bash
npm install --save-dev @vitest-agent/plugin
# or
pnpm add -D @vitest-agent/plugin
```

This brings in the full ecosystem: reporter, UI primitives, engine, SDK, CLI, MCP server, and the native sidecar binary. The plugin is also the **carrier** for the two bins: it declares `vitest-agent` and `vitest-agent-mcp` itself, as four-line shims over `@vitest-agent/cli/main` and `@vitest-agent/mcp/main`. Because the bins belong to the package you installed directly, npm, pnpm, yarn, and bun all link them into `node_modules/.bin/` — no hoisting configuration, no package-manager plugin, no manual step.

Install individual packages directly only when:

| Scenario | What to install |
|----------|----------------|
| Building a custom reporter | `@vitest-agent/reporter` (for contract types and the worked example) |
| Building tooling on the schemas or formatters | `@vitest-agent/sdk` |
| Building tooling on the services or data layer | `@vitest-agent/engine` |
| Building custom rendering | `@vitest-agent/ui` |
| Running the CLI standalone | `@vitest-agent/cli` |
| Running the MCP server standalone | `@vitest-agent/mcp` |

## Versioning

Every `@vitest-agent/*` package versions independently. A change to one package bumps only that package, plus a patch ripple to its workspace dependents so their pins stay current. Because consumers install only `@vitest-agent/plugin` and receive the rest as exact-pinned or ranged dependencies, version skew across the family is invisible to a published consumer.

The Claude Code marketplace plugin (`vitest-agent@spencerbeggs`) also versions independently of the npm packages.
