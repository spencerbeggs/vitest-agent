# @vitest-agent/sdk

The platform-free core of the vitest-agent ecosystem. Carries the Effect Schemas for every domain type, the public reporter and dispatcher contract types, the tagged error classes, the pure formatters and utilities, and the `dispatch` entry the sidecar binary bundles. It has no internal dependencies and no `node:` imports — nothing in this package reads a file, opens a database, or looks at `process`. Every other vitest-agent package depends on it.

The platform half — services, live layers, SQLite, migrations, path resolution, hook programs, and the testing utilities — lives in [`@vitest-agent/engine`](/engine).

Install `@vitest-agent/plugin` for normal use; install `@vitest-agent/sdk` directly only when building tooling on the shared schemas, contracts, or formatters.

## Features

- **Effect Schemas** — all domain types (`RunEvent`, `RenderState`, `AgentReport`, `CoverageTargets`, `TurnPayload`, `ChannelEvent`, identity types) defined with Effect Schema; runtime validation and TypeScript types from one source
- **Reporter and dispatcher contracts** — `VitestAgentReporterFactory`, `ReporterKit`, `ResolvedReporterConfig`, `DispatchInputs`, and the types consumed by every other package
- **Tagged errors** — `DataStoreError`, `PathResolutionError`, `ProjectIdentityNotResolvableError`, the TDD error family, and friends, so a consumer can match on `_tag` without importing the engine
- **Pure formatters** — terminal, GFM, JSON, markdown, CI-annotation, and silent formatters that take a `FormatterContext` and return strings
- **Pure utilities** — `classifyTest`, `computeTrend`, `relativePath`, `classifyTestPath`, `normalizeWorkspaceKey`, and the other helpers that need no I/O
- **Sidecar dispatch core** — `dispatch`, `injectEnv`, and `exitCodeForTag` on the `@vitest-agent/sdk/dispatch` sub-path for a minimal SEA bundle
- **Published JSON schemas** — `@vitest-agent/sdk/schemas/*.json` for validating report files outside TypeScript

## Install

```bash
npm install @vitest-agent/sdk
# or
pnpm add @vitest-agent/sdk
```

## Three entry points

| Entry | Exports | When to use |
|-------|---------|-------------|
| `@vitest-agent/sdk` | Main barrel — schemas, contracts, errors, formatters, utilities | Everywhere except the SEA bundle |
| `@vitest-agent/sdk/dispatch` | `dispatch`, `injectEnv`, `exitCodeForTag` | The sidecar SEA binary; keeps the bundle minimal (no Effect, no SQLite) |
| `@vitest-agent/sdk/schemas/*.json` | JSON Schema documents for the report-file envelopes | Validating `run.json` from non-TypeScript tooling |

The testing utilities that used to ship at `@vitest-agent/sdk/testing` now live at [`@vitest-agent/engine/testing`](/engine#testing-utilities). See [Upgrading to the engine split](/guide/upgrade-engine-split).

## Schemas

Every domain type is an Effect Schema, so the same definition decodes untrusted input at runtime and produces the TypeScript type:

```ts with-api
import { AgentReport, RunEvent } from "@vitest-agent/sdk";
import { Schema } from "effect";

// Decode a report envelope read from disk or received over the wire
const decodeReport = Schema.decodeUnknownEffect(AgentReport);

// The TypeScript type is derived from the same schema
type Event = Schema.Schema.Type<typeof RunEvent>;
```

## Reporter and dispatcher contracts

The SDK defines the contract shapes consumed by `@vitest-agent/reporter`, `@vitest-agent/ui`, and `@vitest-agent/plugin`:

```ts with-api
import type { VitestAgentReporterFactory, ReporterKit, ReporterRenderInput, RenderedOutput } from "@vitest-agent/sdk";

// VitestAgentReporterFactory: (kit: ReporterKit) => VitestAgentReporter
// ReporterKit: resolved config + run-event channel + health info
// ReporterRenderInput: the full report data passed to render()
// RenderedOutput: { target: "stdout" | "github-summary" | "file"; content: string }
```

See [Building a custom reporter](/reporter/custom-reporter) for the worked example.

## Formatters and `FormatterContext`

Formatters are pure functions over an `AgentReport` and a `FormatterContext`. The context carries everything the formatter would otherwise have to discover from the process — including the project root, which is why `cwd` is a required field:

```ts with-api
import { GfmFormatter } from "@vitest-agent/sdk";
import type { AgentReport, FormatterContext } from "@vitest-agent/sdk";

const context: FormatterContext = {
  detail: "standard",
  cwd: "/abs/path/to/project", // required: formatters never read process.cwd()
  noColor: true,
  coverageConsoleLimit: 10,
};

declare const reports: ReadonlyArray<AgentReport>;
const outputs = GfmFormatter.render(reports, context);
// outputs: ReadonlyArray<RenderedOutput>
```

The same rule applies to `relativePath(filePath, cwd)` — pass the root explicitly.

## The pure `dispatch` entry

`@vitest-agent/sdk/dispatch` is the sidecar's whole runtime. It is deliberately I/O-free: the caller hands it a `DispatchIo` object and gets back captured output and an exit code, so the same code runs inside the SEA binary, the JS CLI fallback, and a unit test with a fake file system:

```ts with-api
import { dispatch } from "@vitest-agent/sdk/dispatch";
import { readFileSync } from "node:fs";

const result = await dispatch(["inject-env", "--", "pnpm vitest run"], {
  cwd: process.cwd(),
  env: process.env,
  readFile: (path) => readFileSync(path, "utf8"),
});
// result: { stdout, stderr, code }
```
